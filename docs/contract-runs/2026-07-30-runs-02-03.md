# Contract runs 02 and 03 — 2026-07-30

Two further executions of `npm run test:contract` against the same live tenant,
the same day as run 01. Run 02 tested the corrections from run 01; run 03 tested
the corrections from run 02. See `2026-07-30-run-01.md` for the gate's purpose.

## Run 02

|                   |                                               |
| ----------------- | --------------------------------------------- |
| Commit under test | `0d14149`                                     |
| Result            | **81 cases: 33 passed, 2 failed, 46 skipped** |

Run 01's headline finding was confirmed: `properties` is required on §12.1,
§12.2 and both §12.3 endpoints, and genuinely optional on §12.4. The corrections
shipped in `0d14149` are correct.

Two new findings, both fixed before run 03:

1. **§12.4 `data` can contain a non-array entry.** It came back holding a
   `company` scalar alongside the item classes. The code collected only
   array-valued entries, so that entry was **silently dropped** — an undisclosed
   omission. Non-array entries are now disclosed, and an _unrecognised_ one is
   distinguished from known request metadata.
2. **`componenttypes` ids do not follow the documented `<module>_<group>_<type>`
   composition.** `snmp_common_ups_upsbatteries` carries four segments. The
   server copies these ids verbatim and never composes them, so no product code
   depended on the broken rule.

**46 skipped was itself the finding.** The suite discovered its candidate
modules from `componenttypes` — a platform-wide catalogue — and probed `cisco`,
`clearpass`, `cohesity` and `common`, none of which this tenant polls. No metric
property name could be discovered, so 40 assumptions went UNVERIFIED. Module
discovery now derives candidates from the devices' own `modules` maps.

## Run 03

|                   |                                                |
| ----------------- | ---------------------------------------------- |
| Commit under test | `0d14149` plus the run-02 corrections          |
| Result            | **81 cases: 44 passed, 17 failed, 20 skipped** |

Unverified fell from 40 to 14; the module-discovery fix worked, and 17
assertions that had been skipped now execute.

**Confirmed:**

- `properties` required on §12.1, §12.3 and §12.3-item; optional on §12.4.
- **The `itemType` construction rule holds.** This was inferred from a single
  example and baked into tool descriptions, so it mattered:
  `snmp_americanpowerconversion_uiosensorstatusentries` (from `componenttypes`)
  → 400 unknown component; the singular form built from
  `/system/deviceDefinitions/components` → 200.
- `interval=hour` and `interval=day` accepted; `aggregate` and `alignTimeRange`
  accepted; §12.4 genuinely ignores `limit` (23 items with and without).
- §12.3 returns the documented envelope with real data, in 1–2 seconds.
- The device-ownership pin is sound: records carry an ObjectId `company`, and a
  company-scoped read of a foreign id returns 404.

**The 17 failures are dominated by HTTP 500 from §12.1** —
`{"error":"Sorry, an error occurred. Please try again.","code":500}` — on
queries carrying a valid `properties`, with `lastMetric`, `isMonitored`,
`minIntervals`, `limit`, `interval=minute` and `interval=fiveMin`. A minimal
query did succeed, so the endpoint is **intermittent and query-dependent, not
dead**. §12.2 `/summarize` never returned at all.

Corroborating evidence from the vendor's own web UI: the company dashboard
issued 57 API calls on load, including its "Top devices by CPU" and "Top devices
by memory" widgets, and **never called `/api/v1/metrics/companies/`**. The
vendor's product does not use this endpoint for company-wide metrics.

Owner decision: document §12.1/§12.2 as unreliable and route models to the
device-scoped tools, rather than withholding them. Recorded as M12 in the spec.
