# Contract run 04 — 2026-07-31

A targeted routing probe of every **write** path, against the same live Lumics
tenant as runs 01–03. It differs from those three in each of the ways that
matter, and the differences are why it found what it found.

- It was **not** `npm run test:contract`. It was `curl`, by hand, one request at
  a time.
- It exercised **writes** — `POST`, `PATCH`, `PUT`, `DELETE`. The contract suite
  is read-only by design (D-0006), so nothing it can run reaches a write path at
  all.
- It was not a pre-release gate. It was prompted by a **user bug report**: a
  `lumics_create_ipaddress` call against the published `0.1.0` hung and never
  produced a result.

The report was correct. The cause is a defect in this repository's captured API
contract, and it is one the 0.1.0 gate could not have caught.

## Method

Two things about the method have to be stated plainly, because every conclusion
below rests on them.

**Routing was read off the body, not the status.** This API answers an unrouted
path with an **HTML** error page and a routed path with **JSON**, including when
the routed request finds nothing to act on. Both can carry a 404, so the status
code alone does not separate "no such route" from "no such record". Every claim
here about whether a path exists is a claim about which of those two bodies came
back.

**Nothing was mutated, with one deliberate exception.** Writes were aimed at
bogus 24-hex ids or carried deliberately invalid bodies, so a request that did
route had nothing to change. The single exception was agreed in advance: one
real IP address, `10.30.253.10`, was created in subnet
`6a2b08d1533f5ef7e1c3e8e1` at the user's request, to prove the create path end
to end rather than infer it from a rejection. The subnet's addresses were listed
again afterwards and that record was the only addition. No token endpoint was
called.

## Finding 1 — every ipaddress route is singular; the documented plural is not routed

| Verb     | plural `/ipsubnets/:s/ipaddresses` | singular `/ipsubnet/:s/ipaddresses`  |
| -------- | ---------------------------------- | ------------------------------------ |
| `GET`    | 404, HTML — no route               | **200**                              |
| `POST`   | 404, HTML — no route               | **200**, record created              |
| `PATCH`  | 404, HTML — no route               | **200** `{"updated":null}`, bogus id |
| `DELETE` | 404, HTML — no route               | **500**, bogus id — routed           |

The plural spelling is not a per-verb alternative to the singular. It is not
routed for any verb, and it never was.

Note the last two rows of the singular column. A `PATCH` at an id that does not
exist answers `200 {"updated":null}`; a `DELETE` at the same id answers `500`.
Neither is a success. Both are the API answering in JSON, which is the entire
claim being made: the route is there.

**This is what the bug report was.** Spec §13 Q1 stated that the ipaddress
routes use singular `/ipsubnet/` for the two GETs and plural `/ipsubnets/` for
POST, PATCH and DELETE, and told the reader not to "fix" it. That instruction
was carried into `src/api/paths.ts` and `src/tools/ipam.ts` and shipped, so
`lumics_create_ipaddress`, `lumics_update_ipaddress` and
`lumics_delete_ipaddress` in `0.1.0` addressed a path that does not exist and
could never have succeeded. The two read tools were unaffected and have always
been correct.

**How the spec came to be so confident.** §13 Q1 offered the vendor's own
generated doc slugs as corroboration — `..._ipsubnets_ipSubnet_ipaddresses_post_1060`
and its siblings — reasoning that a slug derived from a route string is evidence
about the route. It is not: it is evidence about the vendor's documentation
generator, and it traces back to the same source as the prose it was offered to
support. Two sources that reduce to one source are one source. That is what
turned a vendor typo into a fact this repository defended in comments and
locked in unit tests.

**Run 01 then appeared to confirm it.** A GET against the plural spelling
returned 404, and §0.4 recorded that as confirming the asymmetry — in the one
section of the spec that instructs the reader not to correct its entries. The
measurement was right and the conclusion was wrong: a read-only run can
establish that the plural is unrouted **for GET** and nothing whatever about a
write path. That entry is now marked `WITHDRAWS` rather than deleted, with the
reasoning left visible, because how it happened is the useful part.

## Finding 2 — `DELETE` of a nonexistent ip address returns 500, not 404

`DELETE /companies/:c/ipsubnet/:s/ipaddresses/<bogus id>` answered **500**. Spec
§3 documents 404 for "not found" and 500 for a server error, and §8.5 documents
neither. A client cannot tell an address that is already gone from an API that
has broken, so a delete tool cannot honestly report "already absent" on this
route. It also means a client that treats 500 as transient will retry something
that fails identically every time; this repository's client does not, because
500 is not in its retryable set.

`PATCH` reports the same condition on the same resource as `200
{"updated":null}`. The two write verbs disagree with each other as well as with
§3.

## Finding 3 — `POST /companies/:c/ipsubnets` with an empty body returns 500, in HTML

A subnet create carrying `{}` — omitting all four fields §10.3 marks required —
answered **500 with an HTML body**. A rejection is correct here; a 400 naming
the missing field is what a required-field table implies. What arrives cannot be
classified by a JSON client at all, because the client fails while parsing and
there is no API answer left to classify. This is the same failure mode as spec
§14 defect 23 (§12.4 on unsupported modules), now seen on a second, unrelated
resource — which makes it a property of the API rather than of the metric layer.
Validate the four required fields client-side; the API's own rejection is
unusable.

## Not a defect — this tenant's token cannot create three of the six resources

`POST` create returned **403 `{"error":"forbidden to access this resource"}`**
on collectors, devices and ipgroups, while `PATCH` and `DELETE` on those same
three resources were permitted and `POST` of an ipaddress succeeded.

**This is recorded as an observation about the tenant's permissions and
explicitly not as an API defect.** An account permitted to modify and delete but
not create is an ordinary role shape, and nothing measured here establishes what
the API grants a differently-privileged token. Whether this account's role is
configured as intended is a question for the tenant's administrator.

It is written down for two narrow reasons. A 403 is JSON from a routed path, so
it says nothing about spelling and must not be mistaken for a routing failure by
a later run. And it bounds finding 1 honestly: the create path was proved end to
end on ipaddresses only; on collectors, devices and ipgroups the probe reached
authorization and stopped.

## Confirmed as documented

Everything else probed matched the vendor's documentation. Recorded because a
probe that reports only its failures misrepresents its own result.

- Write path spellings for **collectors** (§5.3–§5.5), **components** (§6.3),
  **devices** (§7.3, §7.5, §7.7), **ipsubnets** (§10.3–§10.5) and **ipgroups**
  (§9.3–§9.5) are correct as documented.
- **`PUT /devices/:id/modules/:module/lastDiscovery`** (§7.4) — `PUT` is the
  only routed verb on that path. `PATCH` and `POST` both return an HTML 404. The
  vendor documents `PUT` and the vendor is right; normalising it to `PATCH` for
  consistency with the neighbouring device writes would reach nothing.
- **`PATCH /devices/:ids/batch`** (§7.6) is routed as documented.

## Status of the gate

**The 0.1.0 gate was read-only, and that is why this shipped.** D-0006 makes the
contract suite a manual pre-release gate and scopes it to `GET` — no standing
credential in CI, and no writes against a production tenant from a test suite.
That scope was a deliberate decision and it is not being revisited here. But it
has a consequence that was never stated: **no gate this project had could
observe whether a write path exists.** Runs 01–03 reported the metric layer in
detail and said nothing about `POST`, `PATCH` or `DELETE`, and D-0012 recorded
the gate as `PARTIALLY SATISFIED` over the metric layer's unverified remainder
without noting that the entire write surface was outside it.

So `0.1.0` shipped with three tools that could not work, past a gate that was
working as designed. The failure is not that the gate was skipped; it is that
its coverage was described by what it ran rather than by what it could not
reach.

What this run does and does not settle:

- **Settled:** the routing of every documented write path, and the three
  behaviours in findings 1–3.
- **Not settled:** response shapes and semantics of the writes. Beyond the one
  deliberate create, every write was pointed at a bogus id or an invalid body,
  so nothing here verifies what a successful `PATCH` or `DELETE` returns for a
  real record.
- **Not settled:** anything about a differently-privileged token (see the 403
  observation above).
- **Not addressed:** whether the read-only scope of `tests/contract/**` should
  change. A write-capable contract suite against a production tenant is a
  larger decision than this run, and it is not taken here.

The findings are recorded in three places, each for a different reader:

- **`docs/reference/lumics-api-v1.md`** — §0.1, §0.2, §0.3 (M13–M16), §0.4, the
  new §0.5, §8, §10.3, §13 Q1, §14 defects 26–28 and a note on §15. Marked
  `MEASURED 2026-07-31`, set alongside the vendor's original wording rather than
  replacing it, so the drift stays visible.
- **`docs/DECISION_LOG.md`** D-0014 — the decision to correct the captured
  contract against the measurement and ship `0.1.1`.
- **`src/api/paths.ts`, `src/tools/ipam.ts`** and their tests, on branch
  `fix/ipaddress-write-paths-singular` — the correction itself, with the
  superseded reasoning described rather than silently removed.

No new ADR was written. ADR-003 already records the standing decision that a
live measurement outranks the vendor's text where the two disagree, and none of
its five decisions changes because of this run — see D-0014 for the reasoning,
and for the one falsified sentence in ADR-003's evidence section that cannot be
edited in place.
