## Result

**64 cases: 26 passed, 28 failed, 10 unverified.**

27 of the 28 failures shared one root cause — `properties` is required on four
of the five metric endpoints, where the vendor documents it as optional. The
28th was `componenttypes` returning entries missing the documented `type` field.

Findings are recorded in three places, each for a different reader:

- **`docs/reference/lumics-api-v1.md`** §0, §12.5 and §14 defects 17–23 — the
  measurements themselves, marked `MEASURED 2026-07-30` and set alongside the
  vendor's original wording rather than replacing it, so the drift stays visible.
- **`docs/adr/ADR-003-metric-layer-live-contract-corrections.md`** — the
  decisions taken in response, and what remains a vendor gap.
- **`docs/DECISION_LOG.md`** D-0008 to D-0011.

## Status of the gate

**NOT SATISFIED.** This run found defects; the corrections landed in `0d14149`
and have **not been measured against a live tenant**. The credential expired
before a confirming run was possible.

Before tagging `v0.1.0`, run the suite again on `0d14149` or later and record
the result as run 02. What that run needs to establish:

- `properties` is accepted in the form the tools now send, on all four endpoints
- the `itemType` construction rule — `filePath` module/group + `data.itemType`
  joined by `_` — yields ids the metrics API accepts, beyond the single
  `snmp_common_cpu` example it was inferred from
- `/summarize` completes inside the 180-second deadline, or is confirmed as
  exceeding it so the timeout and one-attempt cap can be re-judged
- the silent-failure lock still holds: an invalid `properties` still returns 200
  with empty stats, so the disclosure that depends on it is still warranted

Three assumptions could not be exercised in run 01 and remain open: this tenant
had no component instances in the first five component types; `properties` was
only exercised for module `snmp`; and no successful `/summarize` response was
ever observed, so its response shape is unverified.
