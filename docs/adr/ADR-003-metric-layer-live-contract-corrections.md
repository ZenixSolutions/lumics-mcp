# ADR-003: Metric Layer Corrections from the First Live Contract Run

- **Status:** Approved
- **Date:** 2026-07-30
- **Related RFC:** RFC-001
- **Approved by:** Project Owner

## Context

On **2026-07-30** the read-only contract suite (`tests/contract/**`) ran against a live Lumics tenant for the first time. RFC-001 assumption **A1** — "the vendor documentation matches live behaviour" — was the thing under test, and it did not hold. The measurements are recorded in [`docs/reference/lumics-api-v1.md`](../reference/lumics-api-v1.md): the new [§0](../reference/lumics-api-v1.md#0-live-tenant-measurements--2026-07-30) index of findings, [§12.5](../reference/lumics-api-v1.md#125-measured-metric-behaviour--live-tenant-2026-07-30) for the metric detail, and defects **17–23** in [§14](../reference/lumics-api-v1.md#defects-the-live-api-contradicted-measured-2026-07-30), kept numerically continuous with the documentation defects found on 2026-07-29 but marked as a different kind of finding. That file is the evidence base for everything below; this ADR records what was decided about it, not what was observed.

Four measurements drive this decision:

- **`properties` is required, not optional (M1, defect 17).** Omitting it returns `400 {"error":"Must supply required component metrics as properties parameter"}` on spec §12.1, §12.2 and **both** §12.3 endpoints. §12.0 marks the parameter optional. Taken at face value, the vendor documentation describes four metric endpoints that cannot be called, and this server's four metric tools accordingly could not make a single successful call. On §12.4 the parameter really is optional, and there it acts as a **filter** rather than a projection: supplying `Calculated.cpu` returned `count: 0` instead of a narrowed `stats`.
- **An invalid `properties` value is accepted with HTTP 200 and empty stats (M2, defect 18).** The 400 gate tests presence, never validity. `properties=cpu` (a bare name with no type group) returned **200 with 658 rows, every `stats` an empty object**; `properties=bogusXYZ` returned exactly the same; a real group with an unknown metric echoed the group empty (`{"Rate":{}}`); an unrecognised group produced rows with no `stats` key at all. The syntax the API actually wants is `<TypeGroup>.<metric>`, comma-separated. Groups confirmed present on that tenant: `Calculated`, `Rate`, `TimeTicks`. Confirmed **absent**: `Counter`, `Gauge`.
- **`componenttypes` ids are not `itemType` values (M3, defect 19).** 213 of 246 ids returned by `GET /:context/:contextId/componenttypes/` (§6.4) were rejected as `itemType` with `400 Unknown component <value>`. §6.4 returns a **plural alias**; the metrics API wants the **singular** component id — `snmp_common_cpus` fails, `snmp_common_cpu` succeeds. `itemType` is validated **before** `properties`, so a wrong `itemType` masks the required-`properties` error entirely.
- **§12.2 `/summarize` never returned (M5, defect 21).** Every attempt exceeded **90 seconds** without producing a 200, with and without `itemType` narrowing and with a valid `properties`, while §12.1 and §12.3 answered over the same window and module in **one to two seconds**. Nothing in the vendor documentation mentions cost, scale or timeout on this endpoint.

**Why this needs an ADR rather than a bug fix.** `CLAUDE.md` names two categories an agent must not decide on its own judgement, and this change is in both:

- **Public interface change.** Making `properties` required on four tools changes their argument contract. `standards/ai-interface-standard.md` makes the tool surface the public contract from 0.1.0.
- **Deviation from the captured spec.** `CLAUDE.md` says plainly: do not "fix" the API in code, do not invent parameters or constraints, and "if you believe the spec is wrong about live behaviour, that is a contract-test finding and an issue, not a licence to change the code." Rejecting a `properties` value locally is exactly a constraint the captured contract does not contain.

The Project Owner reviewed the findings and **approved fixing the metric layer for v0.1**. This ADR records that approval and its scope.

### What the run confirmed

An ADR that lists only the failures would misrepresent the evidence. Most of what the documentation says held, including several things this server's design depends on (spec §0.4):

- **There is no pagination anywhere**, exactly as §4.3 documents. List reads are bare arrays with no envelope, total or cursor; `limit` is honoured on devices, collectors and ipgroups; `offset` is ignored. The project's most load-bearing honesty rule rests on a fact that is now measured, not assumed.
- **The IPAM singular/plural asymmetry is real in the deployed API**, not only in the documentation: a GET against the **plural** spelling returned **404**. The singular read path is load-bearing rather than defensive, and the "retry with the other spelling on a 404" idea recorded in §13 Q1 would accomplish nothing for reads.
- **`resourceId()` and the `id`/`_id` split are real** — the ipgroup list returns `id` where the single read returns `_id`, so the helper that tolerates both is doing necessary work.
- **The device-ownership pin is sound.** Device records carry an ObjectId-shaped `company` field, which is what `assertDeviceInPinnedCompany` reads, and a company-scoped read of a device the company does not own returns **404** — so the refusal path is reachable and correct.
- **`dataPoints`/`width` really are required**, which is what RFC-001 D5 item 2 and the always-sent default resolution exist for.
- **`sum=true` (boolean) is rejected with 400**, and an unrecognised `interval` is rejected. RFC-001's account of the prototype's defects — a boolean `sum`, no resolution — is confirmed rather than merely inferred from the documentation.

## Decision

### 1. `properties` becomes a **required** argument on the four metric-data tools

`lumics_get_company_metrics`, `lumics_summarize_company_metrics`, `lumics_get_device_metrics` and `lumics_get_device_item_metrics` all require `properties`. The API rejects the call without it (M1), so this is not a narrowing of a working surface — it is the difference between four tools that cannot succeed and four tools that can.

It is **required rather than defaulted**. A default would have to name a metric, and no metric name is correct for every module: `Calculated.cpu` means nothing under `netapp` or `http`. A defaulted `properties` would turn every unqualified request into a confident, well-formed answer to a question nobody asked, which is the same failure this project designs against everywhere else.

`lumics_get_metric_summary` (§12.4) keeps `properties` **optional**, because there it is genuinely optional upstream and it **filters rather than projects** — supplying it drops items that lack the property instead of narrowing the items that have it. Its description tells callers to start without it.

### 2. Client-side validation beyond the captured spec: a `properties` value with no `Group.metric` entry is rejected locally

`src/tools/schemas.ts` rejects a `properties` value in which **no** comma-separated entry contains an interior dot, before any request is issued. This is a constraint the captured contract does not contain, and `CLAUDE.md` otherwise forbids adding one.

**It is justified by the measurement, not by taste.** An invalid `properties` value does not return an error. It returns **HTTP 200 with the full row count and empty stats** (M2). The API therefore cannot be relied on to reject the value, and the resulting failure is invisible: a well-formed, successful, complete-looking response that establishes nothing. The usual argument for deferring validation upstream — "the API will tell us" — is false here, and measurably so.

**The guard is deliberately the weakest one that still catches the trap.** One qualified entry lets the whole value through, so `Calculated.cpu,status` is accepted even though `status` carries no group. Requiring *every* entry to be dotted would be stronger, but nothing in the evidence establishes that no bare name is ever legal — the vendor's own §12.1 example passes `status` alongside dotted names — and rejecting a value that might work is a worse failure than passing one that might not. What is rejected is only the case measured returning nothing but empty stats: no dotted entry at all.

### 3. A runtime disclosure class for the same trap

When rows come back but the requested property paths are absent or empty across **every** returned row, the tool output says the property names may be malformed. It does not report an empty series.

The disclosure distinguishes total failure (no requested path resolved anywhere: the response establishes nothing about these metrics) from partial (some resolved: the values present are real, the gaps are suspect), and it names which half of each unresolved path looks wrong — an unqualified entry, a recognised group with no such metric, or a group that never appeared at all — because those need different fixes. It fires only when there are rows to inspect: over an empty result it would be a guess, and the existing absent-series disclosure already covers that case.

This is the governing principle of the project applied to a new failure mode. `CLAUDE.md` states it for pagination — "silent truncation reads as completeness. That is the failure mode to design against" — and RFC-001 D5 item 3 states it for result limits. The rule generalises: **a partial or suspect result must never read as a confident negative.** 658 rows of empty `stats` under a successful tool result is exactly that. Left undisclosed, a model reports "these devices are not collecting CPU data" on the strength of a typo, and nothing in the response contradicts it.

### 4. Discovery routing is corrected

- **`lumics_list_component_types` is no longer the route to an `itemType` value.** It returns the plural alias (M3), and 213 of 246 of its ids are rejected by the metric endpoints. The `itemType` argument description now says so explicitly and names the failure (`400 Unknown component`).
- **The singular id is constructed from `GET /system/deviceDefinitions/components`** (§6.5, `lumics_get_device_definition_components`): take the module and group from an entry's `filePath` (`/components/snmp/common/Cpu.yml` → `snmp`, `common`) and join them to the singular `data.itemType` (`cpu`) with underscores → `snmp_common_cpu`. `data.componentAlias` is the plural form §6.4 returns.
- **A row's own `type` field** in a §12.1 or §12.3 response is also a correct `itemType`, so one unfiltered call is a working discovery path.
- **`lumics_get_metric_summary` (§12.4) is documented as the only enumeration path for metric property names**, with both of its limits stated wherever it is offered as one: it surfaces **device-scoped** names only, and its response key is **module-dependent** (`devices` for `snmp`, `http_endpoints` for `http`), so a client must read whichever key arrives rather than looking up `devices`.
- **The ordering trap is documented:** `itemType` is validated before `properties`, so a wrong `itemType` returns `400 Unknown component` and hides a `properties` problem entirely. Fix `itemType` first.

### 5. A per-request timeout override, and a larger budget for `/summarize`

`RequestOptions.timeoutMs` in `src/api/client.ts` overrides `LUMICS_TIMEOUT_MS` for one request. `lumics_summarize_company_metrics` uses it, passing `Math.max(config.timeoutMs, METRIC_SUMMARIZE_TIMEOUT_MS)` where `METRIC_SUMMARIZE_TIMEOUT_MS` is **180,000 ms**, so an operator who has already raised the configured timeout above that keeps their value.

The override is per-request rather than a change to the default: raising `LUMICS_TIMEOUT_MS` itself would make every other tool wait three minutes to discover an unreachable host. It is **not** a tool argument anywhere, so a model cannot ask this server to hold a connection open for minutes; only calling code can set it. 180,000 ms is deliberately not `MAX_TIMEOUT_MS`, and the tool description states plainly that a large tenant can still exceed it and that a timeout there is **a timeout, not evidence that no data exists**.

**The deadline and the retry budget multiply, so `/summarize` also caps its attempts at one.** `RequestOptions.maxAttempts` narrows the client's retry loop for a single request, and the summarize call sets it to `METRIC_SUMMARIZE_MAX_ATTEMPTS = 1`. Without it, a timing-out `/summarize` cost three 180-second deadlines — over nine minutes of silence before anything was reported, which from inside an MCP client is indistinguishable from a hung server — for retries that cannot help, because an endpoint that did not answer in three minutes is not suffering a transient fault.

Three properties of that cap are decided here rather than left to implementation:

- **The per-request value can only lower the budget, never raise it** (`Math.min` against the client-wide `maxAttempts`, not `??`). A per-request option able to *raise* it would be a way to multiply load against an API that documents 429 without documenting any limit (RFC-001 assumption A2), and the concurrency gate would not catch it: that gate bounds requests in flight, not requests in total. An operator who configured a smaller budget keeps theirs.
- **The cap is on attempts, not on one retry class.** The narrower fix — keep the budget for status codes and refuse it only for a timeout — was considered and rejected. Its premise is that a status-code retry is cheap, which holds everywhere else in this API but not here: the retryable statuses this endpoint is most likely to produce are 502 and 504 from an intermediary that gave up waiting on the aggregation, those arrive only after that intermediary's own multi-second deadline, and they repeat deterministically because the next attempt asks for exactly the same expensive work. One number with one meaning gives a worst case of one deadline for *every* failure mode.
- **A `/summarize` timeout is re-explained before it reaches the model.** The generic timeout message names the deadline and the attempt count and stops there, which leaves a model that just asked "how much space is the estate using" one step from answering "no data was found". The enriched error says the endpoint is known to be slow, that it was attempted once **deliberately**, that **this is a timeout and not an empty result** and must not be reported as an absence of data, and what to make smaller — `itemType` first, then `properties`, then the window, or the fast §12.1 endpoint instead. It is also marked not retryable as issued, so nothing downstream reads the generic "timeouts are retryable" flag and reissues it.

The narrowing applies to that one request; the shared `DEFAULT_MAX_ATTEMPTS = 3` is untouched for every other call.

## Consequences

- **Four metric tools can now succeed. Before this change they could not.** The tool-surface change is breaking in form — a previously optional argument is now required — but nothing that previously worked stops working, because nothing previously worked. Recorded in `CHANGELOG.md` under `[0.1.0]` as a breaking tool-surface change with that qualification stated, per the pre-1.0 policy in `docs/RELEASE.md`.
- **Component-level metric property names are discoverable from no endpoint at all.** This is the honest headline consequence and it is not fixed by anything above. §6.5 `deviceDefinitions/components` is the **inventory** schema and carries no metric property names — zero occurrences of `Calculated` or `sysUpTime` across 386 KB, with `data.schema` holding configuration fields such as `ifDescr` and `ifIndex`. §12.4 is the only endpoint that enumerates real property names, and only **device-scoped** ones. `Calculated.ifInOctets` on an interface was found by **probing**, and is obtainable from no documented route. So a model can discover device-scoped names via §12.4 and cannot discover component-level names at all, while decision 1 makes supplying one mandatory and M2 makes a wrong guess look like success. **This bounds what the metric tools can do**: component-level metric questions are answerable only when the caller already knows the name, from the Lumics UI or from institutional knowledge. **It is a vendor gap, not something this server can close** — no amount of client-side work enumerates names the API does not publish. It is recorded in the spec (§12.5 M6, §14 defect 22), stated in the tool descriptions and the runtime disclosure, and should be raised with the vendor.
- **Property names are tenant-specific and are not promoted to code.** `METRIC_PROPERTY_TYPE_GROUPS` (`Calculated`, `Rate`, `TimeTicks`) exists to put concrete legal-looking values in a tool description and **nothing validates against it**. Validating against it would reject a group a different tenant happens to use. `Counter` and `Gauge` are confirmed absent on the measured tenant, which is why the descriptions say so rather than offering them as plausible SNMP type names.
- **The beyond-spec guard can produce a false rejection.** If a bare property name turns out to be legal on some module and a caller sends *only* bare names, this server refuses a call the API would have accepted. The weak form of the guard bounds that cost to the all-bare case, and the error message names the syntax and the enumeration path. This is a deliberate trade: the alternative is the silent-empty-answer failure, and a rejection a caller can read beats an empty answer a caller cannot.
- **§12.2 remains UNVERIFIED.** Its entire documented surface — response envelope, `sum` semantics, `type: "summed"`, `components`, the integer bucket `_id` — was never observed, because the endpoint never returned. The larger deadline makes success possible; it does not make it demonstrated, and the contract suite reports the endpoint as slow/UNVERIFIED rather than asserting a shape it has not seen. Whether the 90-second behaviour is tenant-scale or endpoint-wide is not known from one tenant. Treat any client built on §12.2 as unexercised.
- **The single-attempt cap on `/summarize` gives up a real retry.** A `/summarize` call that fails on a transient 429, 502 or genuine network blip is not retried, where every other read would be. What the model loses is an automatic retry it can perform itself — and a tool call it re-issues is visible and interruptible, which nine silent minutes are not. The error text tells it so.
- **Every metric response is longer.** The disclosure notes are reserved out of `LUMICS_MAX_OUTPUT_CHARS` before the payload is fitted, so on a tight budget the property-coverage note costs rows. That ordering is deliberate and unchanged: a disclosure is never dropped or shortened to make room for data.
- **The reproducibility of these measurements is limited.** One tenant, one company, one point in time, and the credential used has since expired. Every finding is written so the contract suite can re-check it with a fresh token, and none of them is a vendor commitment. A future run that contradicts one of them is a new finding, not a regression.
- **`docs/reference/lumics-api-v1.md` is no longer purely the vendor's documentation.** It now carries dated `MEASURED 2026-07-30` markers alongside the original text, with nothing deleted. That preserves its auditability against the source, and it means every reader has to know the marker convention — which §0.1 states.

## Alternatives Rejected

- **Leave `properties` optional and let the 400 surface to the model.** Rejected: it makes the tool's normal path a guaranteed failure and teaches a model that the metric tools are broken. The error text ("Must supply required component metrics as properties parameter") does not name the syntax, the enumeration path, or the `itemType` masking trap, so a model that receives it has no route to a correct second attempt.
- **Default `properties` to a plausible value such as `Calculated.cpu`.** Rejected: no metric name is correct across modules, and under M2 a wrong default returns a successful empty answer rather than an error. This would manufacture the exact silent failure the disclosure in decision 3 exists to catch, and it would do it on every unqualified call.
- **Validate `properties` strictly — require every entry to be dotted, or check against `METRIC_PROPERTY_TYPE_GROUPS`.** Rejected: the observed group list is one tenant's, and the vendor's own §12.1 example mixes a bare `status` with dotted names. A strict guard would reject calls that may be legal, on evidence that does not support it. The weak guard catches the measured trap and nothing else.
- **Add no client-side validation at all, on the grounds that `CLAUDE.md` forbids deviating from the captured spec.** Rejected, and this is the deviation this ADR exists to authorise. The rule assumes the API rejects what it does not accept. Here it does not: it answers 200. Following the rule literally would mean shipping a parameter whose most likely misuse is invisible to the caller and to the model.
- **Rely on the runtime disclosure alone and drop the input guard.** Rejected: the disclosure fires only when rows come back, so an all-bare `properties` on a query that legitimately returns nothing produces neither a rejection nor a disclosure. The two controls cover different halves of the problem and neither replaces the other.
- **Report an empty-stats response as "no data for this metric".** Rejected outright: it is a confident negative about the estate built on an unvalidated string, and it is the failure this project is organised against.
- **Keep pointing `itemType` at `lumics_list_component_types`.** Rejected on the measurement: 213 of 246 of its ids are rejected by the metric endpoints. Continuing to name it as the route would send a model to a lookup tool whose output is wrong for the argument it is looking up.
- **Translate plural aliases to singular ids inside this server.** Rejected for v0.1: the observed rule (drop a trailing `s`, roughly) is an inference from one tenant's catalogue, not a documented mapping, and 33 of the 246 ids were accepted as-is. A silent rewrite of a caller's argument that is right most of the time is worse than an argument description that says where the correct value comes from.
- **Raise `LUMICS_TIMEOUT_MS` globally to cover `/summarize`.** Rejected: it would make every other tool — all of which answer in one to two seconds — wait three minutes to discover an unreachable host or a hung connection.
- **Expose the timeout as a tool argument.** Rejected: it would let a model hold a connection open for minutes on any endpoint. The override is set by calling code, for the one endpoint whose documented work is genuinely long.
- **Let `/summarize` keep the default three attempts.** Rejected: three 180-second attempts is a nine-minute tool call, and a timeout on an endpoint that aggregates every component in the company is not the kind of failure a retry fixes.
- **Cap only the timeout retry on `/summarize`, keeping the budget for transient statuses.** Rejected: the retryable statuses this endpoint actually produces (502, 504 from an intermediary that gave up on the aggregation) are neither cheap nor transient here, and they repeat deterministically. That leaves 429 as the only genuinely cheap case, and the concurrency gate already exists to avoid it.
- **Allow a per-request `maxAttempts` to raise the budget as well as lower it.** Rejected: a symmetric option is a way to multiply total load against an API with an undocumented rate limit, and the concurrency gate bounds requests in flight rather than requests in total. The option tightens only.
- **Wait for the vendor to fix the documentation before changing anything.** Rejected: the tools do not work in the meantime, and the vendor has made no commitment. The spec file records both the vendor's text and the measurement, so the record stays auditable either way.

## Security and Compatibility Impact

**Security.** No change to the security model. Nothing here touches credentials, redaction, the read-only registration filter, the destructive-operation gates, or the company pin — the pin over the two device-scoped metric tools is unchanged and was independently confirmed sound by the same run. The new client-side validation is an **additional** input check ahead of the API, in the direction `standards/security-standard.md` requires (validate all external input); it removes no check. `componentQuery` and `filters` remain unexposed: ADR-002 decision 3 is untouched, and nothing in these findings argues for reopening it. The one new capability is a longer deadline on a single endpoint, which is a resource-consumption consideration rather than an authorization one: it is bounded by a constant, unreachable from a tool argument, and now capped at one attempt so the worst case is a single 180-second hold rather than a compounding one. Availability risk from a slow upstream endpoint is disclosed in the tool description rather than hidden behind a retry.

**Compatibility.** Making `properties` required is a **breaking change to the tool surface**, which per `standards/ai-interface-standard.md` is the public contract from 0.1.0. Pre-1.0 permits it with a minor bump and an explicit changelog notice, and 0.1.0 is unreleased, so no published consumer is affected. The honest framing — recorded in `CHANGELOG.md` — is that the four tools could not succeed at all before the change, so the break removes a call shape that never worked rather than one anyone relied on. Everything else here is additive or documentary: the `itemType` guidance, the discovery routing, the disclosure notes and the timeout override change no argument name, type or default. `lumics_get_metric_summary` is unchanged in signature. The captured spec file gains measurements alongside the vendor text and loses nothing, so it remains auditable against the source.
